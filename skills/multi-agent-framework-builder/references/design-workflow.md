# 设计与生成流程

## 需求到框架

优先从用户消息与现有仓库获取这些信息，不机械一次性提问：

| 维度 | 影响的决定 |
|---|---|
| 产品目标、使用者、核心流程与成果 | 哪些任务、怎样验收 |
| 现有项目/技术栈/项目规范 | 可复用组件和修改边界 |
| 平台、OS、Agent 工具和执行范围 | 原生调用还是通用交接；角色配置位置 |
| 可并行模块和共享文件 | 分工、依赖与整合策略 |
| 授权、网络、成本与运行时长约束 | 可运行操作、预算与停止条件 |
| 验证类型与证据 | 单测、集成、数据校验、视觉或内容审查 |
| 断点恢复和历史任务规模 | 状态、快照和日志需要多详细 |

只生成框架时不要求用户提供模型密钥。若承接真实 API 开发，用实际授权与目标环境凭据规范处理。
已提供需求足以设计时先落地，未知项写在设计说明中。不能把示例项目内容复制到新项目。

## 从最少角色开始

主 Agent 负责目标、接口约定、依赖、状态、资源归属、整合与验收决策。执行者负责约定任务及自测。
验证者根据需求和实际产物检查，不把开发者“完成了”当证据。

需要时增加：架构/规划角色、前后端或数据执行者、集成者、特定验证者。增加角色应对应可区分的职责与价值，避免只多几个名字。
主 Agent 可在小项目中承担规划、公共接口和整合；用户要求纯调度才禁止其实现代码，并明确谁负责公共部分。
验证维度根据项目产生：UI 检查截图/交互，API 检查接口和授权，数据检查定义/质量，内容检查来源/覆盖。不得固定为布局、美观、动画。

## 任务、并行与所有权

一个任务是可交付、可验收的业务/技术单元，不能按固定行数切分。
先确定跨模块接口，再并行实现。依赖未通过前下游不进入执行；发现新依赖更新图，不能隐式依赖未交付内容。

并发上限=min(平台允许的子 Agent 数、资源容量、可独立写入的任务数、用户预算约束)。先区分平台上限是否包含主 Agent，未知时保守串行或低并发。
批量大小与并发分别配置；一个执行者批量处理多个任务也必须为每个任务保留独立状态与验收。

同一文件只能有一个当前写入所有者。模块可声明 write scope；多个角色需要改共享接口时交给整合者或串行处理。
Git worktree 可用于独立 checkout，用户要求或目标环境允许时使用；不强制所有环境具备 Git，不以创建大量分支替代任务边界。
测试可以生成临时文件和 evidence，但不能修改被检验的实现。仅声明只读却给予不受限 shell 时，注明仍是约定而非强制沙箱。

## 输出工作包

优先沿用目标仓库路径。无约定时使用 `.agent-framework/`，该目录是本技能默认约定，不是某平台配置格式。

```text
.agent-framework/
  README.md                 # 用户与主 Agent 启动方式、当前验证范围
  project-brief.md          # 目标、流程、范围、确认事实与待定项
  framework-design.md       # 角色、依赖、所有权、预算与选择理由
  runtime.md                # 真实能力、调用映射、权限/生命周期
  quality-gates.md          # 项目专属验收与证据要求
  framework.json            # 协议定义的角色、策略和任务状态
  agents/                   # 主 Agent 与所需执行/验证角色提示词
  tasks/                    # 每任务交接包、执行报告与审查报告
  evidence/                 # 实际检查/测试/截图，不提前伪造
  recovery.md               # 恢复顺序与已知失败处理
```

有真实执行后再生成 `events.jsonl`、checkpoint 和经验记录；不要为了树形结构创建假日志/假证据。
机器状态是任务真相来源；README 或 plan.md 只是其摘要，避免两个任务清单各自手工维护冲突。
顶层已有 AGENTS.md 时保留其内容，按需合并短入口或在工作包提供主入口，不覆盖原规范。

任务交接至少含：目标、明确不做的范围、需求锚点、输入及版本、依赖、允许写入路径、验收项、证据目录、预算、报告格式。
不能只传素材路径却不说明需完成什么；不能强制所有执行者读全仓库。

## 运行时适配

在 runtime.md 逐项写实际能力与对应工具：spawn、状态查询/等待、消息、唤醒、resume、取消、持久化 ID、工作区隔离、权限。
未知能力写 unsupported/unverified；不从旧笔记推断当前 API 参数或路径。
可恢复句柄只是优化；每个任务的持久化交接包才是恢复基础。原执行者不可恢复时新建等效执行者并记录关联，不让“必须 resume”成为永久阻碍。
真正后台调度需要平台调度/等待机制或服务进程；单个提示词不能保证会话结束后持续运行。

## 试运行与交付

先做无外部副作用的协议演练：正常任务过门禁；失败后修复并重测；相同文件争用被串行化；旧报告被拒绝；丢失 Agent 用交接包恢复；预算耗尽后停派。
生成框架不等于已执行这些任务。演练记录说明 synthetic/file-based 或真实工具运行，不能伪造 ID。
只为生成框架不启动实质业务；用户要求试跑时选择低风险代表任务，符合已有授权。

交付入口提示词和文件路径，说明选择理由、运行能力未验证项、完成标准与下一步。
产品型多 Agent 服务还应有 Mission、技术架构、接口、状态存储和部署实现；可使用环境提供的项目基础文档技能，不能用文件协作约定替代工程实现。
