# 多 Agent 框架生成器

接收一个项目需求，为承接项目的主 Agent 生成可直接使用的协作工作包。产物应回答：谁做什么、根据什么做、在哪写、如何交接、怎样验证、失败怎么办，以及上下文丢失后如何继续。

完整读取 [设计与生成流程](references/design-workflow.md) 和 [协作契约与恢复机制](references/protocol.md)。创建角色时读取并按需求改写 `assets/` 中的 [主 Agent](assets/orchestrator.md)、[执行 Agent](assets/worker.md)、[验证 Agent](assets/reviewer.md) 模板。模板是设计起点，不是必须复制的最终角色体系。

## 执行范围

默认完成项目专属框架文件、角色提示词、任务清单和流程演练；不因生成框架自动启动业务开发、部署云服务或付费运行。
用户同时要求开发时可在已有授权范围内执行生成的计划。只有当前平台确实提供且用户授权时才启动子 Agent；框架文件生成不依赖真实子 Agent。

区分两类需求：

- **开发协作框架**：让主 Agent 调用平台已有子 Agent，共同完成软件/内容任务。默认采取此模式。
- **产品内的多 Agent 服务**：用户要开发可部署的调度/持久化服务。此时还需明确 API、租户、数据库、队列、部署和模型预算；不能把提示词目录声明为服务实现。

不明确但不影响框架初版的选择记录假设并继续；必须确定的权限、部署或成本选择才询问。继承用户指定技术栈和模型，不凭参考文件固化模型品牌、路径或 API。

## 生成流程

1. 读需求和目标仓库，检查已有 AGENTS.md、代码、计划与执行环境。记录确认事实、设计决定、假设和待定问题。
2. 判断可独立验证的任务与共享资源，设计最少必要角色和依赖图。角色、并发、批量和验证维度按项目选择。
3. 按协议明确角色读写边界、工具权限、交接内容、证据要求、预算、重试和恢复行为。仅写提示词不能声明已实现权限隔离。
4. 在用户输出位置生成真实可用工作包：项目说明、框架设计、主入口、角色、运行能力映射、机器可读任务状态、质量标准与恢复说明。
5. 若用户已指定执行平台，核查该平台现有工具/文档后生成可支持的配置；不假造 `.claude`、Codex 或其它平台参数。未知平台先生成通用提示词和人工交接模式，清楚标明尚未接入运行时。
6. 按当前项目设计演练成功交付、失败修复、Agent 丢失/恢复、并发冲突、过期报告、预算耗尽路径。文件演练与真实调用分别记录。
7. 运行结构检查脚本，核对需求→角色→任务→验证的一致性，再交付明确启动方式和尚未验证的运行能力。

默认角色可以是主 Agent + 执行 Agent + 验证 Agent；小型任务可由一个执行角色完成，复杂系统才按职责扩展。不要以代码行数拆任务，不为每个步骤强行创建角色。

## 不变量

- 调度 ID 来自该次官方工具返回或可靠运行记录，不按全局最新文件推断；缺少 resume 能力时可以带持久化交接包重建执行者。
- 任务完成须有当前版本验收证据。超时、重试耗尽、预算耗尽均不转换为通过；受影响任务暂停/失败/等待用户，并处理独立任务。
- 主 Agent 读紧凑任务摘要、关键问题和证据索引，必要时查看原文；不盲信 PASS/FAIL，也不默认读全量历史日志。
- 每个写入资源有明确所有者；共享文件由单个整合者提交，或使用隔离工作区/队列串行修改。提示词约定不等于操作系统强隔离。
- 验证者不修改实现，但可在指定 evidence 目录写报告、测试结果与截图。测试命令的写入/网络/费用边界也需明确。
- 确认每份报告的 task_id、attempt、artifact_revision 和验收项，拒绝旧通知替代新结果；晚到结果进入事件记录，不改变已取消或更新任务。
- 恢复前先核查输出、在途工作和实际副作用；不能因为日志缺一行而重复外部写入。

结构检查（只验证保存的协议字段、任务依赖和完成证据，不验证实际业务结果）：

```text
python <skill目录>/scripts/validate_framework.py <生成框架目录>
```

本技能依据用户两份旧版/项目专用参考改写，没有采用其中未经核验的理论归属或平台实现细节作为事实。
